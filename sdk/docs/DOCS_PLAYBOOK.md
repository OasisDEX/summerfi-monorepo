# How to work with the SDK docs (`gitbook/`)

This repo publishes SDK documentation to a GitBook space from the `gitbook/` folder. Some of that
folder is source you write by hand; most of it is build output. Editing the wrong part gets your
changes silently overwritten (or rejected by CI). This doc says which is which.

## The three kinds of content

| Path                                                                | Who writes it   | How it gets there                                                                |
| ------------------------------------------------------------------- | --------------- | -------------------------------------------------------------------------------- |
| `gitbook/reference/**`                                              | Nobody, by hand | Generated by TypeDoc from TSDoc comments in the SDK source (see below)           |
| `gitbook/SUMMARY.md`                                                | Nobody, by hand | Generated by `scripts/docs/assemble.mjs` from `scripts/docs/summary.template.md` |
| `gitbook/guides/*.md`, `quickstart.md`, `README.md`, `changelog.md` | You, by hand    | Plain prose — write and edit these directly                                      |
| `scripts/docs/summary.template.md`                                  | You, by hand    | Controls the **Guides** nav order/labels; the reference section is a marker      |
| `sdk/*/README.md`, other package `README.md`s                       | You, by hand    | Not part of this pipeline at all — see "Package READMEs" below                   |

**Rule of thumb:** if a file lives under `gitbook/reference/` or is `gitbook/SUMMARY.md`, don't
hand-edit it — your edit will be silently discarded the next time someone runs `pnpm docs:gen`, and
if you commit a hand-edit that drifts from a regeneration, `pnpm docs:check` (which runs in CI on
every PR touching these paths) fails the build.

## Regenerating

```bash
pnpm docs:gen    # pnpm build:sdk && typedoc && node scripts/docs/assemble.mjs
pnpm docs:check  # docs:gen, then `git diff --exit-code -- gitbook` — this is what CI runs
```

Run `docs:gen` after touching anything that affects generated output — TSDoc comments,
`typedoc.json` or a per-package `sdk/*/typedoc.json`, or `scripts/docs/summary.template.md` — and
commit the resulting `gitbook/` diff in the same PR. `docs:check` will otherwise fail on `dev`.

## 1. API reference (`gitbook/reference/`) — edit the TSDoc, not the markdown

TypeDoc converts three packages (`sdk-common`, `sdk-client`, `sdk-client-react` — see `entryPoints`
in `typedoc.json`) plus whatever they re-export (e.g. `armada-protocol-common`, `protocol-plugins`
types flow in through `sdk-common`/`sdk-client`'s public exports). To change a reference page, edit
the doc comment on the exported symbol and regenerate.

### TSDoc, not JSDoc — the tags that don't work

TypeDoc follows [TSDoc](https://tsdoc.org/), not classic JSDoc. A symbol's **name** comes from the
code and its **summary** is just the plain prose at the top of the comment — before any block tag.
These tags are legal JSDoc but **unknown to TypeDoc** and will warn / render wrong if used:

- `@name X`, `@method X`, `@interface X`, `@class X`, `@enum X`, `@implements X` — redundant, delete
  them; the name and kind are inferred from the declaration.
  - **Exception:** a **bare** `@interface` (no argument) is a real TypeDoc modifier — put it on a
    `type X = z.infer<typeof Schema>` alias to force it to render as an interface with resolved
    property listings instead of an opaque `z.infer<...>` line. See `IArmadaDeposit`,
    `IArmadaWithdrawal`, `Transaction` in `sdk-common` for the pattern.
- `@description text` — unwrap it: delete the tag and move `text` into the leading prose instead.
  That prose becomes the rendered summary; a comment with only `@description` and no leading prose
  renders with no summary at all (you'll see a stray "## Description" section instead).
- `@dev text` — not a TSDoc tag. Use `@remarks text`, or fold it into the leading prose if it's the
  only content in the comment.
- A comment may have **at most one** `@remarks` and **at most one** `@returns` — TypeDoc silently
  drops all but the first if you write more than one; merge them into a single block instead.

### `@param` on object parameters — use the dotted form

Almost every SDK method takes a single destructured `params` object. TypeDoc requires
`@param params.fieldName` to attach a description to a destructured field — a flat
`@param fieldName` (matching the _old_ JSDoc habit of naming the conceptual argument, not the actual
parameter) doesn't match the real parameter name and TypeDoc **silently drops the description** with
a build-time warning, not an error, so this drifts unnoticed:

```ts
// Wrong — "chainId" doesn't match the real parameter name ("params"); silently dropped.
/**
 * @param chainId The chain to query
 */
getVaultInfoList(params: { chainId: ChainId }): Promise<...>

// Right
/**
 * @param params.chainId The chain to query
 */
getVaultInfoList(params: { chainId: ChainId }): Promise<...>
```

Zero-argument methods and methods with plain (non-destructured) parameters use plain `@param name`
as normal. Don't add `@param` docs to `_params`-prefixed stub parameters (methods not yet
implemented) — TypeDoc still checks the name against the (unused) parameter and warns.

### Which layer's TSDoc actually renders — document the client layer

Only the three entry-point packages are converted, so a method's comment reaches GitBook **only**
through what those packages export. This decides where to spend doc effort:

- **Service layer is IDE-only.** `armada-protocol-service` classes (e.g. `DCAManager`, `RWAManager`)
  and the `armada-protocol-common` service interfaces they implement (e.g. `IDCAManager`,
  `IRWAManager`) are **not** re-exported through `sdk-common`/`sdk-client`, so their comments are
  hover-help only — never a reference page. Keep the service interface **lean** (a one-line summary
  per method).
- **The GitBook-facing contract is the client layer.** For a manager that's its `sdk-client` surface,
  and **both** the `I<X>Client` interface **and** the concrete `<X>Client` class are exported from
  `sdk-client/src/index.ts`, so TypeDoc emits a page for each. Put the **canonical rich prose on the
  interface** — summary, dotted `@param`, `@returns`, and `@throws`/`@example` where useful.
- **Handlers are IDE-only.** `sdk-server` tRPC procedures and `sdk-client-react` handlers are not
  exported from their package index, so they never render.
- **`sdk-common` domain types do render** — give each an interface-level summary plus inline per-field
  `/** */`.

### The DRY rule — `@see`, not duplicated prose

Write the canonical prose **once, on the interface**; the implementing class (and handlers) carry only
a `/** @see I<X>Client.method */` one-liner (or `@see I<X>Manager.method` for the service/handler
layers). The codebase uses this in ~800 `@see` sites; `@inheritDoc` is **not** used.

How the impl class page renders — params always come from the type signature; the difference is the
summary/tags:

- **`@see` one-liner (the convention)** → the impl page shows the **signature + params only**; the
  interface's summary / `@throws` / `@example` are not copied onto it (the `@see` counts as the
  member's own, summary-less comment). This is the accepted norm — e.g. `OracleManagerClient`,
  `DcaManagerClient`, `RwaManagerClient` render params-only pages, with the full prose on the
  interface page beside them.
- **No comment at all** → TypeDoc fully inherits the interface comment (summary + params + tags) onto
  the impl page.

Prefer the `@see` one-liner (consistency + a go-to-interface breadcrumb). Either way **no prose is
duplicated** — the interface is the single source of truth. Note the service interface and the client
interface are **parallel types** (no `implements` between them), so prose can't auto-flow between
them: keep the service interface lean and invest the full prose in the client interface. DCA
(`sdk.dca.*`) and RWA (`sdk.rwa.*`) are the reference implementations of this pattern.

### Only exported symbols get a page

TypeDoc only documents what's reachable from a package's public entry (`src/index.ts`), even for
types referenced by something that _is_ exported — e.g. a client interface returned by a manager
property, or a helper type used inside another type's fields. If you see a warning like:

```
X, defined in .../Y.ts, is referenced by Z but not included in the documentation
```

either export `X` from that package's `src/index.ts` (type-only export if it's a type — no runtime
behavior change) or, if it's genuinely internal, leave it and ignore the warning.

### External types (viem, etc.) inlined into our docs

`sdk-client-react`'s `useSDK` hook accepts viem wallet/public clients as parameters, so TypeDoc
inlines viem's own type surface — and tries to parse viem's own doc comments, which reference pages
that don't exist in our docs. Per-package `sdk/*/typedoc.json` sets `excludeExternals: true` to stop
this; `typedoc.json`'s `externalSymbolLinkMappings` sends any external symbol that still gets
referenced to its own docs site instead of warning.

**Config gotcha:** with `entryPointStrategy: "packages"` (see root `typedoc.json`), TypeDoc
_conversion_-time options like `excludeExternals` must live in the **per-package**
`sdk/<package>/typedoc.json`, not the root config — the root config only controls the _packages_
entry point strategy itself and output location, not how each package is converted.

### Verifying a TSDoc change is comment-only

If you're bulk-editing comments (a codemod, a sweep across many files) and want to prove you didn't
touch any code, parse both versions with the TypeScript compiler API, print with comments stripped,
and diff:

```js
import * as ts from 'typescript'
const strip = (src, name) => {
  const sf = ts.createSourceFile(name, src, ts.ScriptTarget.Latest, false, ts.ScriptKind.TSX)
  return ts.createPrinter({ removeComments: true }).printFile(sf)
}
// strip(before, file) === strip(after, file)  →  comment-only change
```

This is the standard the last few docs PRs (#1361, #1373, #1374) held themselves to — every non-code
TSDoc-only commit was verified this way before merging.

## 2. Guides (`gitbook/guides/*.md`) — free-form prose

These are hand-written walkthroughs (deposits, withdrawals, positions, RWA vaults, etc.), one file
per topic. Write them like you'd write any other markdown doc: prose, fenced code samples, and
relative links into `gitbook/reference/...` for symbols you mention (e.g.
`../reference/@summerfi/sdk-client/interfaces/IArmadaPosition.md`).

**Verify code samples against the real interfaces before writing them** — copy-pasting a plausible
API shape from memory is how guides drift. Grep the actual method signature in
`sdk/sdk-client/src/interfaces/` (or wherever it lives) and match parameter names, return types, and
enum values exactly.

To add a new guide, create the file under `gitbook/guides/` and add one line to
`scripts/docs/summary.template.md` under the `* [Guides](...)` block — that template is hand-edited;
only the `<!-- @generated:sdk-reference -->` line below it is a marker `assemble.mjs` expands. Run
`pnpm docs:gen` afterward so `gitbook/SUMMARY.md` picks up the new entry.

## 3. Package `README.md` files — a separate, unrelated system

`sdk/*/README.md`, `packages/*/README.md`, `apps/*/README.md`, and the root `README.md` are **not**
part of the GitBook/TypeDoc pipeline at all — nothing generates them, nothing checks them against
source, and `pnpm docs:gen`/`docs:check` never touch them. They're hand-maintained package-level
docs covering what a package does, its key exports, build commands, and — the part that goes stale
fastest — a "Cross-package connections" section (Consumes / Consumed by / Gotchas) describing how
the package fits into the rest of the monorepo.

Because nothing enforces them, they drift silently whenever the code they describe changes.
`AGENTS.md` (repo root) has the same problem at a higher level — its per-feature checklists
reference specific file paths, config field names, and constants that get renamed or removed. There
is no automated check for either; keeping them accurate is a manual (or agent-assisted) audit
against the actual code, ideally done whenever a change touches the area a README/checklist
describes.

**Filename case matters — watch for `README.MD` vs `README.md`.** If you author a new README on a
case-insensitive filesystem (macOS, Windows) in a directory that already has one with different
casing, your editor/OS will treat them as the same file, but git tracks them as two distinct paths.
The result: a case-duplicate that's invisible to you locally but real in the repo — on
case-sensitive systems (Linux, this repo's CI) both files literally coexist, and on another
contributor's case-insensitive machine, checkout produces a case conflict with unpredictable
resolution. Before adding or renaming a README, run `find <dir> -iname 'readme.md'` and confirm
there's exactly one hit. This bit us once already (8 packages ended up with both `README.md` and a
stale `README.MD` after #1361).

## Where this fits together

- Changed a method's on-chain behavior or added a parameter? Update the TSDoc comment on the
  interface, run `pnpm docs:gen`, commit the `gitbook/reference/` diff.
- Added a new capability worth a walkthrough (like RWA vault exposure)? Add a `gitbook/guides/*.md`
  page and a `summary.template.md` line.
- Restructured how a package depends on others? Update that package's `README.md` "Cross-package
  connections" section and check `AGENTS.md` for any checklist that names the same files.
- Not sure which bucket a doc falls in? If `pnpm docs:gen` would overwrite it, it's generated —
  don't hand-edit it, edit its source instead.
